# 高温设施规划 Agent：产品经理面试说明手册

## 0. 使用方式

这份文档用于面试前准备，目标是帮助你用产品经理视角讲清楚《高温设施规划 Agent》这个项目。它覆盖项目背景、用户痛点、需求拆解、Agent 必要性、工作流、空间 RAG、记忆管理、约束机制、评测方案、技术边界和常见追问。

面试表达主线：

> 这个项目解决的是城市极端高温治理中“知道哪里热之后，下一步怎么治理”的问题。我把基层用户的一句治理目标拆成风险、人群、设施、可达、缺口、候选点、约束、方案和审议九个判断，再用 Agent 做任务转译、任务编排、工具调用、项目记忆、局部重算和可审议输出。

## 1. 项目一句话说明

高温设施规划 Agent 是一个将高温治理目标转译为空间分析任务，并生成可审议清凉设施布点方案的规划智能体。

更口语的面试版本：

> 用户只需要输入“优先保障老人和接送学家庭，在高温风险区补充清凉设施”，系统会自动拆成风险诊断、人群暴露、设施覆盖、步行可达、缺口识别、候选点生成、方案比选和人工核验，帮助规划人员从“知道哪里热”走到“知道怎么治理”。

## 2. 我为什么做这个项目

### 2.1 真实问题

在极端高温治理场景里，很多基层部门已经能看到热力图、人口分布和设施点位，但治理动作仍然很难生成。用户知道哪里热，也知道哪里有人，却很难回答：

- 先治理哪里；
- 补什么类型设施；
- 设施放在哪个点；
- 为什么推荐这个点；
- 公平、效率、成本、应急之间如何取舍；
- 哪些结果可以直接讨论，哪些需要现场核验。

### 2.2 两个断点

| 断点 | 真实表现 | 产品机会 |
|---|---|---|
| 基层治理需求与规划专业能力之间的断点 | 基层人员能提出目标，但不会拆成风险、人群、设施、可达、缺口等专业任务 | 用 Agent 把自然语言目标转译成规划任务链 |
| 空间数据识别与治理行动生成之间的断点 | 热力图、人口、POI 能识别问题，但不能直接生成点位方案 | 用工作流把数据分析转成候选点、方案比选和审议材料 |

### 2.3 用户价值

对基层治理人员：降低专业分析门槛，快速获得可讨论方案。  
对责任规划师：把经验流程化，减少重复分析和材料整理。  
对规划咨询团队：提升初版方案生成和汇报材料准备效率。

## 3. 目标用户与使用场景

| 用户 | 用户目标 | 当前做法 | 主要痛点 | 产品帮助 |
|---|---|---|---|---|
| 基层治理人员 | 快速判断哪里需要补清凉设施 | 依靠投诉、巡查和经验 | 无法说明推荐依据，难以拆专业任务 | 输入治理目标后获得缺口、候选点和核验清单 |
| 责任规划师 | 把治理诉求转成专业方案 | 手动叠加风险、人口、设施、路网数据 | 分析链条长，约束调整后重复重算 | 自动生成任务图、候选点排序和方案比选 |
| 规划咨询团队 | 形成可汇报材料 | 手工整理图表、说明和清单 | 证据链分散，交付准备成本高 | 输出证据摘要、不确定性和审议材料 |

典型输入：

> 优先保障老人和接送学家庭，在高温风险区补充清凉设施。

典型输出：

- 候选点清单；
- 推荐优先级；
- 推荐理由；
- 覆盖人群和步行改善；
- 公平、效率、低成本、应急方案比选；
- 证据摘要；
- 不确定性说明；
- 人工核验清单。

## 4. 需求拆解逻辑

我的拆解起点是用户的一句治理目标，并将它展开成完整决策链。

用户原话：

> 优先保障老人和接送学家庭，在高温风险区补充清凉设施。

拆解为九个判断：

| 决策判断 | 用户真正想知道 | 系统任务 | 输出 |
|---|---|---|---|
| 风险判断 | 哪里热 | 风险诊断 | 高温风险区 |
| 人群判断 | 哪些重点人群暴露 | 人群暴露分析 | 老人、接送学家庭暴露热点 |
| 设施判断 | 现有设施够不够 | 设施覆盖分析 | 覆盖率、服务盲区 |
| 可达判断 | 能不能走到 | 步行可达分析 | 可达范围、未覆盖人口 |
| 缺口判断 | 哪里同时热、人多、设施不足 | 缺口识别 | 缺口热点排行 |
| 候选点判断 | 设施放哪里 | 候选点生成 | 推荐点位 |
| 约束判断 | 点位能否落地 | 空间约束检查 | 冲突项、核验项 |
| 方案判断 | 多目标如何取舍 | 方案比选 | 公平、效率、低成本、应急方案 |
| 审议判断 | 哪些结论能进入讨论 | 材料生成 | 证据摘要和人工核验清单 |

面试表达：

> 我把用户的一句话转成了规划决策链，再把决策链转成任务链。这样 Agent 才有明确执行路径，输出也能被规划师审议。

## 5. 为什么选择 Agent 形态

### 5.1 普通 Dashboard 的局限

Dashboard 能展示热力图、人口和设施，但用户仍然需要自己判断下一步。它适合看数据，缺少任务编排能力。

### 5.2 普通 Chatbot 的局限

普通 Chatbot 可以回答问题，但容易直接生成自然语言建议。规划场景需要数据依据、工具调用、状态记忆和人工核验。

### 5.3 Agent 的产品价值

| Agent 能力 | 解决的问题 | 在本项目中的体现 |
|---|---|---|
| 任务转译 | 用户输入模糊 | 把治理目标转成结构化任务 |
| 任务编排 | 不知道先做哪一步 | 生成 taskGraph 和前置任务 |
| 工具调用 | 需要空间分析能力 | 调用风险、覆盖、缺口、候选点等工具 |
| 状态记忆 | 多轮对话容易断裂 | 保存项目目标、证据、版本和重算记录 |
| 约束重算 | 用户会反复调整方案 | 判断保留结果和重算起点 |
| 可审议输出 | 城市治理需要证据链 | 输出依据、不确定性和人工核验项 |

面试表达：

> 我选择 Agent 形态，是因为这个问题的核心是连续规划工作流。Agent 可以把用户目标转成任务图，按依赖调用工具，并把结果写回状态，支持后续追问、约束调整和方案追溯。

## 6. 产品架构说明

当前产品可以分为五层：

| 层级 | 作用 | 用户价值 | 关键实现 |
|---|---|---|---|
| 理解层 | 识别用户意图和任务类型 | 用户用自然语言表达即可 | `intentRouter.js`、`llmIntentAdapter.js` |
| 规划层 | 拆解任务、检查前置条件、生成任务图 | 保证分析链条完整 | `planningEngine.js` |
| 执行层 | 调用空间分析和规划工具 | 把数据转成结果 | `registries.js`、工具执行逻辑 |
| 记忆层 | 保存对话、项目、过程和证据 | 支持追问、复用和局部重算 | `projectMemory.js`、`AgentState`、`ragMemory` |
| 输出层 | 生成候选点、方案比选和报告 | 便于审议和汇报 | `ReferenceStateCockpit.jsx`、报告导出 |

## 7. 工作流设计

以输入“优先保障老人和接送学家庭，在高温风险区补充清凉设施”为例：

1. **识别治理目标**  
   系统判断这是高温设施规划问题，进入规划工作流。

2. **提取结构化信息**  
   提取目标人群为老人和接送学家庭，设施对象为清凉设施，策略偏好为公平优先。

3. **判断任务类型**  
   判断为候选点生成任务。

4. **检查前置条件**  
   检查是否已有风险诊断、人群暴露、设施覆盖和设施缺口结果。

5. **自动补齐缺失任务**  
   缺少前置结果时先补齐，避免直接生成点位。

6. **生成任务图**  
   将任务组织成依赖链，确保风险、人群、设施、可达、缺口、候选点、比选顺序清晰。

7. **计划审查**  
   检查任务是否缺输入、是否跳过前置条件、是否存在不可执行步骤。

8. **执行任务并写回状态**  
   工具输出写入 AgentState，供后续任务和多轮对话复用。

9. **输出可审议结果**  
   展示候选点、推荐理由、方案比选、证据摘要和人工核验清单。

10. **支持后续调整**  
   用户新增约束后，系统判断影响范围并局部重算。

## 8. 空间 RAG 设计

### 8.1 为什么需要空间 RAG

规划问题里很多问题是空间事实查询，例如：

- 哪里设施缺口最大；
- 北京林业大学附近有没有设施缺口；
- 上地十街热风险等级是什么；
- 五道口和中关村哪个更缺清凉设施；
- 除此之外呢。

这些问题需要先查地图数据和候选点数据，再组织回答。模型负责表达，数据判断来自检索结果。

### 8.2 当前 RAG 链路

1. 用户输入空间问题；
2. `intentRouter` 判断是否进入 `spatial_rag`；
3. `spatialRag` 解析查询类型；
4. 查询 `showcase.json` 和 `place-index.json`；
5. 构造 `evidencePackage`；
6. 生成有证据的回答；
7. 写入 `ragMemory` 支持追问。

### 8.3 支持的问题类型

| 问题类型 | 示例 | 输出 |
|---|---|---|
| 全区缺口排行 | 哪里设施缺口最大 | 缺口热点排行、道路、推荐依据 |
| 连续追问 | 除此之外呢 | 读取上一轮 ragMemory 继续展示 |
| 地点周边查询 | 北京林业大学附近有没有设施缺口 | 周边缺口、候选点、人工核验 |
| 道路风险查询 | 上地十街热风险等级是什么 | 道路风险等级和数据边界 |
| 片区对比 | 五道口和中关村哪个更缺 | 对比结论和证据 |

### 8.4 RAG 的约束

- 地点、道路、候选点、缺口必须来自地图数据；
- 数据未命中时明确说明未命中；
- 不补造地图中没有的地点、人口、覆盖率；
- 回答中说明检索范围、命中对象、排序依据和人工核验项。

面试表达：

> 我把空间问题交给 RAG，由地图数据和候选点数据提供判断依据。LLM 只负责把检索到的证据组织成用户能理解的回答，点位、道路、缺口和排行都来自地图数据。

## 9. 意图路由设计

### 9.1 为什么需要意图路由

用户既会问专业问题，也会问普通问题，例如“今天天气怎么样”“你好”“讲个笑话”。如果所有问题都强行进入规划流程，体验会很生硬；如果所有问题都交给 LLM，空间事实又容易失控。

### 9.2 路由分类

| 路由 | 典型问题 | 处理方式 |
|---|---|---|
| empty | 空输入 | 提示输入治理目标 |
| date | 今天几号 | 普通回答，不触发工作流 |
| casual_weather | 今天天气怎么样 | 结合天气状态回答，不写入规划状态 |
| capability | 你能做什么 | 说明 Agent 能力 |
| spatial_rag | 哪里设施缺口最大 | 进入空间 RAG |
| map_fact | 某地有没有缺口 | 查询地图事实 |
| planning_knowledge | 设施缺口怎么计算 | 方法解释 |
| planning_workflow | 生成候选点方案 | 进入规划工作流 |
| general_chat | 普通闲聊 | 正常回答，不污染规划状态 |

### 9.3 产品价值

- 普通问题自然回答；
- 空间问题优先查数据；
- 规划目标进入工作流；
- 闲聊不改项目状态；
- 连续追问能读取记忆。

## 10. 记忆模块设计

### 10.1 记忆定位

当前实现的是“项目级规划记忆”，保存一个连续规划项目中的对话、项目状态、任务过程和空间证据。

对应实现：`src/agent/projectMemory.js`

### 10.2 四层记忆

| 记忆层 | 记录内容 | 用户价值 |
|---|---|---|
| conversation | 最近输入、回答、路由、是否规划相关 | 支持追问和防止闲聊污染规划状态 |
| project | 研究区、目标人群、设施类型、策略、约束、候选点 | 保持项目上下文稳定 |
| process | 任务图、工具调用、版本、重算提示 | 支持局部重算和方案追溯 |
| evidence | ragMemory、检索范围、图层、命中对象、核验项 | 支持空间追问和证据链 |

### 10.3 防污染规则

| 问题类型 | 写入位置 | 是否改变方案 |
|---|---|---|
| 普通聊天 | conversation | 否 |
| 天气日期 | conversation | 否 |
| 空间查询 | conversation + evidence | 否，除非用户触发工作流 |
| 规划目标 | conversation + project + process | 是 |
| 约束调整 | conversation + project + process | 是，并生成重算提示 |

### 10.4 局部重算

用户说“避开学校门口”时：

- 可保留：风险诊断、人群暴露、设施覆盖；
- 重算起点：候选点生成；
- 影响任务：空间约束检查、点位排序、方案比选、报告摘要；
- 记录位置：`process.recalculationHints`。

面试表达：

> 记忆模块让 Agent 同时保存对话、项目目标、空间证据、任务过程和方案版本。这样用户可以连续追问，可以新增约束，可以局部重算，也可以追溯每个候选点和方案的依据。

## 11. 工具调用设计

### 11.1 工具调用原则

工具调用设计从用户任务反推所需能力，再映射到具体分析工具。

| 用户任务 | 所需能力 | 输出 |
|---|---|---|
| 找高温风险区 | 风险诊断 | 高温风险区 |
| 找重点人群暴露 | 人群暴露 | 暴露热点 |
| 判断设施够不够 | 设施覆盖 | 覆盖率、服务盲区 |
| 判断步行是否合理 | 步行可达 | 可达范围 |
| 找缺口 | 缺口识别 | 缺口热点 |
| 推荐点位 | 候选点生成 | 候选点清单 |
| 排除不可落地点 | 约束检查 | 冲突项、核验项 |
| 给点位排序 | 多指标评分 | 优先级 |
| 比较策略 | 方案比选 | 四类方案 |
| 形成材料 | 报告生成 | 审议材料 |

### 11.2 调用流程

1. Planner 根据任务图选择工具；
2. 执行前检查输入是否齐全；
3. 工具返回结构化结果；
4. 结果写回 AgentState；
5. 后续任务读取状态；
6. 输入缺失时触发补充任务或人工提示。

### 11.3 当前边界

当前阶段使用 mock 工具和本地数据验证产品结构，后续可替换为真实 GIS、空间分析 API、步行路网、设施台账和现场核验系统。

## 12. 约束机制设计

面试官很可能会问：“你怎么避免大模型瞎编？”

可以从八个约束回答：

| 约束机制 | 解决的风险 | 做法 |
|---|---|---|
| 任务类型约束 | 问题被误判 | 先路由到普通问答、RAG、方法解释或规划工作流 |
| 工作流模板约束 | 跳过关键步骤 | 候选点生成必须经过风险、人群、覆盖、缺口 |
| 前置条件约束 | 缺数据出结论 | 缺少前置结果时自动补齐 |
| taskGraph 约束 | 执行顺序混乱 | 用依赖图组织任务 |
| ToolRegistry 约束 | 随意调用能力 | 只能调用已注册工具 |
| PlanReviewer 约束 | 错误计划进入执行 | 执行前检查输入和依赖 |
| 输出结构约束 | 回答不可审议 | 固定输出证据、候选点、核验项 |
| 人工核验约束 | AI 过度决策 | 权属、消防、施工、开放时间进入核验清单 |

面试表达：

> 我没有让大模型直接生成规划结论。模型前面有意图路由和任务约束，中间有任务图和工具注册，后面有输出结构和人工核验。空间事实必须来自 RAG 或工具结果。

## 13. 三页产品流程说明

### 13.1 第一页：治理目标与风险诊断

功能定位：

- 用户输入治理目标；
- Agent 理解目标并拆解任务；
- 地图展示高温风险、重点人群、设施缺口等基础分析；
- 形成从目标到任务链的第一步。

面试讲法：

> 第一页解决的是“用户说了一个治理目标，系统能不能理解并转成规划任务”。

### 13.2 第二页：候选点生成与核验

功能定位：

- 地图展示候选点空间分布；
- 候选点清单支持点击定位；
- 地图与候选点清单大小可交互调整；
- Agent 持续回答候选点依据、设施缺口、空间证据等问题。

面试讲法：

> 第二页解决的是“哪里适合补设施，以及为什么推荐这些点”。这页的核心围绕候选点展开，同时保留智能体沟通入口，保证从第一页的治理目标延续到点位解释。

### 13.3 第三页：方案比选与报告

功能定位：

- 比较公平优先、效率优先、低成本优先、应急优先；
- 选择方案后地图候选点随之变化；
- 输出方案推荐依据和不确定性；
- 支持生成审议报告和核验清单。

面试讲法：

> 第三页解决的是“多个方案如何取舍，以及如何形成可汇报材料”。

## 14. 输出设计

### 14.1 候选点方案

包含：

- 候选点名称；
- 推荐优先级；
- 服务人群；
- 覆盖人口；
- 步行改善；
- 推荐理由；
- 人工核验事项。

### 14.2 方案比选

包含：

- 公平优先；
- 效率优先；
- 低成本优先；
- 应急优先；
- 推荐方案；
- 取舍说明。

### 14.3 审议材料

包含：

- 背景；
- 方法；
- 数据来源；
- 候选点结果；
- 方案比选；
- 不确定性；
- 人工核验清单；
- 下一步建议。

## 15. 评测方案

| 评测项 | 目标 | 方法 | 通过标准 |
|---|---|---|---|
| 需求理解准确性 | 是否理解用户真实目标 | 构造多类自然语言输入 | 正确识别人群、设施、策略 |
| 任务拆解完整性 | 是否覆盖规划链条 | 对照标准任务链 | 不跳过风险、覆盖、缺口 |
| 前置条件检查 | 是否避免缺数据出结论 | 删除前置状态测试 | 自动补齐缺失任务 |
| 工具选择正确性 | 是否调用合适能力 | 检查任务与工具匹配 | 空间问题走 RAG/地图事实 |
| 状态写回正确性 | 是否支持复用 | 生成结果后追问 | 能读取上一轮结果 |
| 局部重算准确性 | 约束调整是否精准 | 输入新约束 | 正确判断保留结果和重算起点 |
| 输出可审议性 | 结果能否用于讨论 | 专家检查输出 | 有证据、边界、核验项 |
| 人工核验完整性 | 风险是否被标注 | 检查清单 | 包含权属、消防、施工、开放时间 |
| 用户可用性 | 基层用户是否看得懂 | 任务测试和访谈 | 能说明下一步动作 |
| 效率对比 | 是否提升效率 | 与人工流程计时 | 初版方案明显更快 |

## 18. 常见面试追问与回答

### 18.1 产品价值类

**Q1：这个项目的核心价值是什么？**  
回答要点：把高温风险识别推进到治理行动生成；降低基层使用空间分析的门槛；让规划师得到可审议方案。

**Q2：为什么用户需要它？**  
回答要点：基层用户能描述问题，但难以拆成风险、人群、设施、可达和缺口分析；产品把目标变成任务链。

**Q3：和普通 GIS Dashboard 的区别是什么？**  
回答要点：Dashboard 展示数据，本产品组织任务、调用工具、保存状态、输出方案和核验清单。

**Q4：和普通 Chatbot 的区别是什么？**  
回答要点：普通 Chatbot 主要回答文本，本产品有任务图、工具调用、RAG 证据、项目记忆和审议输出。

### 18.2 Agent 必要性类

**Q5：为什么一定要 Agent？**  
回答要点：规划是多步骤任务，需要目标理解、前置检查、任务编排、工具执行和状态复用。

**Q6：Agent 在这里承担什么角色？**  
回答要点：任务编排器，把用户目标转成结构化任务，并组织工具按依赖执行。

**Q7：怎么保证它不会乱跑？**  
回答要点：意图路由、工作流模板、前置条件、taskGraph、ToolRegistry、PlanReviewer 和输出结构共同约束。

### 18.3 空间 RAG 类

**Q8：空间 RAG 解决什么问题？**  
回答要点：地点、道路、缺口、候选点、排行类问题需要查地图证据，RAG 让回答有数据依据。

**Q9：数据未命中怎么办？**  
回答要点：明确说明当前地图索引未命中，提示换地名、扩大范围或重新计算，不补造结论。

**Q10：连续追问怎么处理？**  
回答要点：上一轮 RAG 写入 ragMemory，追问读取 lastResults 和 shownResultCount 继续返回。

### 18.4 记忆模块类

**Q11：为什么需要记忆？**  
回答要点：规划是连续决策，用户会追问、改约束、切策略，记忆支持复用、局部重算和追溯。

**Q12：记忆保存什么？**  
回答要点：conversation 保存对话，project 保存项目状态，process 保存任务过程，evidence 保存空间证据。

**Q13：如何避免记忆污染？**  
回答要点：普通聊天只写 conversation；空间查询写 evidence；规划工作流才写 project 和 process。

### 18.5 约束与安全类

**Q14：怎么避免大模型瞎编？**  
回答要点：空间事实来自 RAG 和工具；候选点、人口、覆盖率不能由模型生成；输出必须带证据和核验项。

**Q15：为什么要人工核验？**  
回答要点：权属、消防、施工、开放时间和安全责任需要现场确认，AI 输出服务于审议。

### 18.6 评测类

**Q16：怎么评估这个 Agent 有效？**  
回答要点：从需求理解、任务拆解、工具选择、状态写回、局部重算、输出可审议和人工效率对比评测。

**Q17：成功标准是什么？**  
回答要点：用户能用自然语言得到有证据的候选点和方案比选，约束调整后能快速生成新版本。

### 18.7 商业化与扩展类

**Q18：可以扩展到哪些场景？**  
回答要点：养老设施、公服设施、应急避难点、公园绿地、防涝设施等，核心都是目标转译、空间分析、候选点和审议输出。

**Q19：如果真实落地，优先接什么数据？**  
回答要点：高温风险、人口与重点人群、现有设施台账、步行路网、POI、权属和现场核验数据。

## 19. 面试收束表达

可以用这段作为最后总结：

> 这个项目的关键是把规划师的分析流程产品化。用户提出治理目标后，Agent 负责拆解任务、检查前置条件、调用空间分析、保存项目记忆、支持约束重算，最后输出候选点、方案比选、证据摘要和人工核验清单。它的价值在于把空间数据从“看见问题”推进到“形成可审议治理方案”。
